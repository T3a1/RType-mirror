# Technical and comparative study

This page explains why R-Type is built the way it is: for each technology, what
we chose, what we compared it with, and what the choice costs us. How the code
works is in the [architecture](ARCHITECTURE.md); this page is about why.

Figures about our project come from the code or from our own
[network benchmark](NETWORK_COMPARISON.md). The comparisons with other
technologies are qualitative: we did not build the game once per alternative.

## Summary

| Topic | Choice | Main alternatives | Deciding reason |
|-------|--------|-------------------|-----------------|
| Language | C++20 | Rust, C#, Go | Required by the subject; C++20 makes the code simpler |
| Graphics, input | Raylib, behind an interface | SFML, SDL | Simplest API that does what we need; the interface kept the choice open |
| Network library | Asio, behind an interface | Raw sockets, ENet | Portable sockets with no protocol imposed on us |
| Transport | UDP with our own reliability | TCP, QUIC | A late game state is useless: never wait for a lost packet |
| Serialization | Explicit binary format | JSON, Protocol Buffers | Small packets, no dependency, every field validated by hand |
| Game architecture | Our own ECS with sparse sets | Inheritance, archetypes, EnTT | Decoupled systems, and the engine is the point of the project |
| Network model | Authoritative server, full snapshots | Lockstep, delta compression | Cheat-resistant and tolerant to loss, at the cost of bandwidth |
| Storage | Text files, no database | SQLite, binary files | The game only has configuration to keep, and people edit it by hand |
| Build, packages | CMake, Conan | Plain Make, vcpkg, system packages | Required portability, dependencies not installed system-wide |

## 1. Programming language

The subject requires C++, so the real choice was the standard and how to use it.
We use **C++20**, for what makes the code shorter and safer: designated
initializers for component and message structs (`{.x = 1.0F, .y = 2.0F}`),
`std::span` for buffers with their size, `std::ranges` algorithms, and
`std::chrono` durations instead of raw numbers for time.

For the record, here is how the usual alternatives compare for this kind of game:

| Language | For this project | Against |
|----------|------------------|---------|
| **C++20** (chosen) | Control over memory layout, which an ECS relies on. All the graphics libraries of the subject are native to it. | No memory safety: malformed packets are a real risk, handled in [section 6](#6-security). |
| Rust | Memory safety at compile time, which matters for a network parser. | Not allowed by the subject. Fewer game libraries, and the team would have to learn it. |
| C# | Productive, garbage collected. | Garbage collection pauses in a 60 Hz loop need care; not allowed by the subject. |
| Go | Simple concurrency, good for servers. | Weak ecosystem for the client's graphics; not allowed by the subject. |

## 2. Graphics, audio and input

The subject suggests SFML and allows others such as SDL or Raylib, but not game
engines or libraries with too broad a scope.

| Library | For | Against |
|---------|-----|---------|
| **Raylib** (default) | Very small API: a window, textures, text and keyboard take a few calls. Includes audio and a default font. Simple to build through Conan. | C API; fewer features for complex UIs. |
| SFML 3 | C++ API, well known. | Needs a font file to draw text (we ship DejaVu Sans for it). |
| SDL 3 | Most portable, widely used in commercial games. | Lower level: text and image loading need extra libraries, so more code on our side. |
| ncurses | Runs in a terminal, over SSH, with no GPU. | Character cells, no textures, one key at a time. Not a real alternative, but a proof that the rendering is decoupled. |

**Decision.** We chose Raylib for its simplicity. The risk of a wrong choice was
removed by hiding the library behind `client::gfx::IGraphics`
(`client/include/graphics/IGraphics.hpp`). Only `client/src/graphics/<backend>/`
includes a graphics library. To prove that the interface really works, we wrote
three backends: Raylib, SFML and ncurses. You choose one at build time with
`./rtype.py -g sfml`.

**Input** goes through the same interface, since windowing libraries own the
keyboard events.

**Audio** follows the same pattern with its own interface, `client::audio::IAudio`
(`client/include/audio/IAudio.hpp`). Raylib and SFML both include audio, so each
client uses the library it already links, and adds no dependency to choose. ncurses
has none, so its client stays silent, like a client on a machine with no audio device.
The sounds are generated by a script instead of being downloaded: they contain no
third-party content, so they raise no license question.

## 3. Networking

### 3.1 Network library

| Option | For | Against |
|--------|-----|---------|
| **Asio** (chosen), standalone | Portable sockets on Linux and Windows, header-only, no Boost needed. Imposes no protocol. | Its asynchronous model is more than we need: we only use its sockets, with our own loop. |
| Raw BSD sockets, Winsock | No dependency. | Two versions to write and maintain, for Linux and Windows. |
| ENet | Reliability over UDP already done and proven. | It would decide the protocol for us, and the protocol is a large part of the project. |
| SFML network | Comes with SFML. | Ties the server to SFML, while the server must build with no graphics library. |

Asio is **hidden** behind `engine::net::IUdpSocket`, and linked as a private
dependency. Network code can therefore be tested on an in-memory fake socket,
with simulated loss and no real network.

### 3.2 Transport: UDP or TCP

The subject requires UDP for in-game traffic. It is also the right choice:

| | TCP | UDP (chosen) |
|---|-----|--------------|
| A lost packet | Blocks everything behind it until it is resent | Only that packet is missing |
| Effect on the game | The player waits for a position that is already outdated | The next snapshot, 50 ms later, replaces it |
| What we had to build | Nothing | Reliability for the few messages that need it |

QUIC would give independent streams over UDP, but it brings encryption and a
large library for a game that sends positions.

**Two delivery modes** are enough ([protocol, section 7](PROTOCOL.md#7-reliability)):

- Inputs and snapshots are **unreliable**: each carries a newer state and
  replaces the previous one.
- Events such as `EntityDestroyed` are **reliable and ordered**: acknowledged,
  and resent every 100 ms until they are.

### 3.3 Protocol format

| Format | Size of one entity | For | Against |
|--------|-------------------:|-----|---------|
| **Custom binary** (chosen) | 16 bytes | Smallest, no dependency, the format is documented like an RFC | Written by hand, with version management |
| JSON | About 60 bytes | Readable, easy to debug | About 4 times larger at 20 updates per second, and slow to parse |
| Protocol Buffers | Between the two | Generated code, compatible versions | A code generator and a dependency for about 16 messages |

We never `memcpy` a struct onto the network: padding and byte order would depend
on the compiler. Each field is written and read explicitly, in little-endian.
This also means that every field is validated when it is read.

The whole format is in the [protocol document](PROTOCOL.md), written so that
someone can write a new client from it alone.

### 3.4 Network model

| Model | For | Against |
|-------|-----|---------|
| **Authoritative server** (chosen, required by the subject) | One truth, so a modified client cannot cheat on positions, hits or scores | Each action needs a round trip, which [prediction](#35-hiding-the-latency) hides |
| Lockstep | Little bandwidth, used by strategy games | Everyone waits for the slowest player; a loss freezes the game |
| Peer to peer | No server to host | No authority, and players see each other's addresses |

**Full snapshots or deltas.** Each snapshot sends every entity, 20 times per
second. Delta compression would send less, but it needs acknowledged baselines
and much more code, and full snapshots tolerate loss without any special case.
The cost is measured: [at 5 kB/s the game falls behind](NETWORK_COMPARISON.md#5-analysis)
once enemies are numerous. Deltas would be the first thing to add for slow links.

### 3.5 Hiding the latency

The Part 2 networking track adds three techniques. Their effect is
[measured](NETWORK_COMPARISON.md):

| Technique | What it solves | Result on the benchmark |
|-----------|----------------|-------------------------|
| Entity interpolation | 20 snapshots per second look choppy on a fast screen | Frozen frames fall from 92 % to under 2 % |
| Client prediction and reconciliation | The local ship reacts only after a round trip | Input delay falls from about 150 ms to 0 at 100 ms of round trip |
| Several games on one server | One game per process wastes machines | Up to 16 rooms, each with its own thread and registry |

**Not done on purpose: server-side lag compensation.** It would rewind the targets
to what the shooter saw. It adds a position history on the server, and the team
kept its time for graded items. Players therefore aim at enemies drawn 100 ms in
the past while the server decides on their real positions.

## 4. Algorithms, design patterns and data structures

### 4.1 Existing techniques we selected

| Need | Choice | Compared with | Why |
|------|--------|---------------|-----|
| Organize game objects | **Entity Component System** | Inheritance tree (`Enemy : Entity`) | The subject asks for decoupled subsystems. Rendering only needs a position and a sprite, not health. A new behavior is a new component, not a new branch of a tree. |
| Store components | **Sparse sets** | Archetypes, `std::map` | O(1) add, remove and lookup, packed iteration. Archetypes iterate faster but move entities between tables whenever a component changes, which is not worth it for a few thousand entities. |
| Reference an entity safely | **Index + generation** | Raw pointers, plain ids | A stale handle is detected instead of silently pointing at a new entity. |
| Destroy during iteration | **Deferred destruction** | Immediate removal | Removing would invalidate the iteration in progress. |
| Run the simulation | **Fixed time step with an accumulator** | Variable time step | The subject forbids depending on CPU speed. The same inputs give the same result on any machine. |
| Exchange data between threads | **Mutex around a queue, emptied all at once** | Lock-free queues | The lock is held only for a few moves, so contention is negligible, and it is simple enough to be sure it is correct. |
| Detect collisions | **All pairs of axis-aligned boxes**, filtered by layer | Spatial grid, quadtree | O(n²), but the game has few entities on screen. A grid would be the next step if profiling asked for it. |
| Compare sequence numbers | **Serial number arithmetic** (as in RFC 1982) | Plain comparison | Keeps working when 16-bit sequence numbers wrap around. |

### 4.2 Design patterns

| Pattern | Where | Why |
|---------|-------|-----|
| Bridge (an interface and its backends) | `IGraphics`, `IUdpSocket` | Library code stays in one directory, and tests can use a fake |
| Factory | `server::EntityFactory` | One place knows which components make an enemy or a missile |
| Command | `SpawnCommands` | Systems request entities and they are created at one point of the tick, so the registry never changes during an iteration |
| Scheduler with stages | `engine::Scheduler` | The order of the systems is data, not code scattered in a game loop |
| Producer and consumer | `engine::MessageQueue` | The game thread never touches a socket and the network thread never touches the registry |

### 4.3 What we wrote ourselves, and why

| Component | Instead of | Why we wrote it |
|-----------|-----------|-----------------|
| The ECS (`engine/`) | EnTT, Flecs | Building the engine is the heart of the project. Ours has only what the game uses. |
| `ReliableChannel` | ENet, KCP | About 70 lines, tested, and exactly the semantics the protocol documents. |
| `InstanceManager` | One process per game | One port for every room, with game-agnostic code in the engine. The cost is that a crash stops every room. |
| `CommandConsole` | A remote admin protocol | The console stays local, so it adds nothing to attack over the network. |
| Logger | spdlog | Adapted from a team member's project ([Blackbox](https://github.com/Thomas-Peze28/Blackbox)). A writer thread keeps the game from waiting on the terminal or the disk. |
| Enemy movement patterns | A scripting language | Sine, zigzag and dive are data in level files, which is enough for the waves we need. |

## 5. Storage

The game has **no database and no account**: a game lives in memory and ends with
its room. What remains to store is configuration:

| Data | Where | Format | Written by |
|------|-------|--------|------------|
| Levels | `server/levels/*.json` | JSON | The developers |
| Weapon settings | `server/weapons.json` | JSON | The developers |
| Enemy and boss kinds | `server/enemies.json` | JSON | The developers |
| Banned and allowed addresses | `--banlist`, `--whitelist` files | Text, one address per line | The server (console commands) |
| Key bindings | `controls.cfg` | Text, `action = keys` | The client (Settings page), or the player by hand |
| Volumes, video and accessibility options | `settings.cfg` | Text, `name = value` | The client (menu pages), or the player by hand |
| Benchmark results | `build/netbench/*.csv` | CSV | The client, with `--bench` |

### Comparison

| Technique | Persistence | Reliability | Constraints | Verdict |
|-----------|-------------|-------------|-------------|---------|
| **Text files** (chosen) | Survive restarts | No transaction: a crash during a write can lose a file | Editable with any editor, readable in Git | Fits configuration that changes rarely |
| SQLite | Survives restarts | Atomic transactions | A dependency, and the server image has no writable storage by default | Worth it if the game stores scores or accounts |
| Binary files | Survive restarts | Same as text, plus version problems | Small, but not editable by hand | No benefit: these files are tiny |
| Server database (PostgreSQL...) | Durable, shared | Very high | A service to run for every server | Far too heavy for this game |
| Memory only | Lost at restart | None | Fastest and simplest | What we use for the game state, which has no value after the game |

### Reliability in practice

- **Size limits**: a level file is refused above 1 MiB, the weapon file above
  64 KiB, the enemy file above 256 KiB, so a wrong file cannot exhaust the memory.
- **Validation**: a level is checked field by field. An invalid one is skipped and
  reported with its position (`waves[4].count: must be a whole number from 1 to
  20`), and the server still starts.
- **Limit**: the ban list is rewritten in place. A crash in the middle of a write
  could lose it. Writing to a temporary file and renaming it would make this atomic.
- **Limit**: in Docker, the image holds only the binary and its data. To keep a ban
  list across restarts, it needs a mounted volume.

## 6. Security

### 6.1 Main vulnerabilities and what we do about them

| Technology | Vulnerability | What the project does | What remains |
|------------|---------------|-----------------------|--------------|
| C++ | Memory errors when parsing untrusted data | Fixed-size receive buffer; counts checked against the bytes present before anything is reserved; randomized tests with hundreds of thousands of mutated datagrams ([`packet_fuzz_test.cpp`](https://github.com/T3a1/RType-mirror/blob/dev/tests/src/packet_fuzz_test.cpp)); clang-tidy `bugprone-*` as errors in the CI | The CI does not run AddressSanitizer or a coverage-guided fuzzer |
| UDP | Forged source address | A session is tied to an address and a port | **Known limit**: no handshake token. A forged `Connect` takes a session slot for 5 seconds ([protocol, section 10](PROTOCOL.md#10-robustness-rules)) |
| UDP | Flood of packets | Queues with a capacity; 64 sessions at most; 256 unacknowledged reliable packets per peer | No rate limit per address, so a flood still costs CPU |
| Custom protocol | Malformed or oversized packets | Validation order documented and tested; an invalid packet is dropped whole; a version mismatch is refused | |
| Custom protocol | No encryption or authentication | Nothing sensitive is sent: no account, password or personal data | Anyone on the path can read or forge a game's traffic |
| Client | Cheating with a modified client | Authoritative server: a client only sends which keys are held | It can still automate its inputs |
| JSON files | Malicious or broken file | nlohmann-json, size limits, validation of each field | These files come from the server's operator, not from players |
| Console | Unauthorized administration | It reads the server's terminal only, and nothing listens on the network | Whoever reaches the terminal controls the server |
| Docker | Compromised server process | Static binary in a `scratch` image: no shell, no libc files, runs as `nobody` | A library fix needs a rebuild of the image |
| Dependencies | A vulnerable or replaced package | Exact versions in `conanfile.py`, no copy in the repository | `alpine:3` follows the latest 3.x, on purpose |
| CI | Theft of the deploy key | The key is a repository secret, and the workflow only runs on `push`, so a pull request from a fork never gets it | GitHub Actions are pinned by tag, not by commit |

### 6.2 Data integrity

- **In transit**: the header's magic, version, type and exact payload size must all
  match. There is no checksum of our own: UDP has one, and each field is validated.
- **Game state**: only the server changes it, on one thread per game, and systems
  run single-threaded. Reliable messages arrive in order and exactly once.
- **On disk**: see [section 5](#5-storage).

### 6.3 Monitoring in the long term

| What | How | State |
|------|-----|-------|
| Every change | CI on every push: build, unit tests, clang-tidy, formatting, Docker image. A red CI blocks the merge into `main` and the push to the Epitech repository. | In place |
| Base image | The server image is rebuilt from `alpine:3` on each push and launch, so it follows the fixes of Alpine. | In place |
| A running server | Timestamped logs (`docker logs`) and the console: `status`, `rooms`, `players`, `banlist`. Refused addresses are logged, and invalid packets at debug level. | In place, read by hand |
| Vulnerabilities in dependencies | Check the versions in `conanfile.py` against the [GitHub Advisory Database](https://github.com/advisories) before each release, and update through Conan. | **Manual procedure** |
| Automatic alerts | Dependabot could watch the GitHub Actions and the Docker image. It does not know our Conan dependencies. | Not set up |
| Attack detection | Counting invalid packets per address and exposing the counter in `status` would show a flood or a scan. | Not done |

## 7. Accessibility

The game draws on what actual games do. This table lists only what exists today;
the rest is tracked in the project's issues.

| Category | What exists | Inspired by | Still to do |
|----------|-------------|-------------|-------------|
| **Physical and motor** | All keys remappable in the Settings page or in `controls.cfg`, with two keys per action. Default keys for either hand, so the game can be played with one hand. Auto-fire, so firing needs no repeated presses, which an option can turn on at the start. Menus work with the keyboard alone or the mouse. | Remapping and toggle options of most PC games | Game speed, controller |
| **Visual** | Player colors from the Okabe-Ito palette, which color-blind players can tell apart. Not color alone: by default, each ship shows "P1" and "(you)", an option the player can turn off, and notices name the player. The keyboard selection is marked with `>`, not only by a color. | Color-blind modes of multiplayer games | Scalable game UI, high contrast |
| **Audio** | Sound is never the only cue: shots, explosions, the charge glow, the level banner and the game over screen show on screen what the sounds tell. Separate volumes for the music and the sounds, saved between sessions; a volume of 0 turns it off. | Volume settings and visual cues in most action games | Nothing planned |
| **Mental and cognitive** | Short menus, a few clear actions, a "Level 2" banner and final scores. A How to play page shows the rules and the player's own keys. Three difficulty levels and the choice of the starting level, picked in the waiting room. | Difficulty settings of most action games | Reducing flashing effects |

**The documentation**: online pages with a search bar and an outline; a light or dark
theme that follows the reader's system; images with a visible caption; headings in
order for screen readers. Each chart of the benchmark also has its figures in a table. Mermaid
diagrams are explained in the text around them.

**Why it matters for these choices**: making controls data (`controls.cfg`) and
player identity text (labels) cost almost nothing at design time. Adding them
later would have touched every input and drawing system.

## 8. Tools

| Topic | Choice | Compared with | Why |
|-------|--------|---------------|-----|
| Build | CMake | Make, Meson | The standard for C++ on Linux and Windows, and required by Conan's toolchain |
| Packages | Conan | vcpkg, system packages, Git submodules | The subject forbids relying on system-wide libraries or copying dependencies. Conan's packages work the same on our platforms. |
| Server image | Alpine, static musl binary, `scratch` | Debian-based image | A very small image with nothing to attack. So the server cannot use Conan there, hence the Alpine packages. |
| Launcher | Python (`rtype.py`) | Shell script | The same script on Linux and Windows; it replaced `rtype.sh` |
| Tests | GoogleTest | Catch2 | Includes mocks, widely known |
| Code quality | clang-format, clang-tidy | Review only | Enforced by the CI, with one pinned clang-format version for everyone |
| Documentation | Doxygen, for the pages and the code reference | MkDocs, Sphinx, a wiki | One tool for one website: the pages stay in Markdown beside the code and are reviewed in pull requests, and they can link to the code reference. It draws our Mermaid diagrams and has a search bar. The limit is that this search only covers titles, headings and code names, not the text of the pages. A second generator would have added full-text search and a second tool to maintain. The French pages are a second Doxygen run, under `fr/`, and a small script adds the language button. |

## 9. Before and after: the Part 1 prototype and the final version

Measured on 2026-11-06, against the `v1.0` tag (2026-10-18).

| | Part 1 (`v1.0`) | Now |
|---|----------------|-----|
| C++ code (lines, with headers) | 8,210 | 30,000 |
| Unit tests | 86 | 375 |
| ECS systems (source files) | 20 | 33 |
| Protocol version | 1 | 12 |
| Games on one server | 1 | Up to 16 rooms, with a lobby |
| Graphics libraries | Raylib, called directly | Raylib, SFML, ncurses, behind an interface |
| Network library | Asio, visible in the code | Hidden behind an interface, tested on a fake network |
| Game loop | Written by hand in each program | `engine::Scheduler`, with stages and conditions |
| Entity creation | Direct, during the tick | Requested, then created at one point of the tick |

**Architecture.** The engine now holds what another game would reuse: scheduler,
instance manager, socket interface, command console. Library code moved behind
interfaces, and the game loops became a list of systems.

**Performance**, from [the benchmark](NETWORK_COMPARISON.md), for the same build
with each technique turned off, at 100 ms of round trip:

| | Part 1 behavior | Final |
|---|----------------|-------|
| Delay between a key press and the ship moving | About 150 ms | 0 ms |
| Frames where an entity is frozen | 92 % | Under 2 % |
| Largest moves of an entity per frame (99th percentile) | 22.6 units | 3.9 units |
| Upload of the client at 240 frames per second | About 4 kB/s | About 0.5 kB/s |

**Features.** Sprite sheets and animations instead of colored rectangles; new enemy
types with movement patterns; levels, weapons and enemies in JSON files; two
end-level bosses; obstacles and destroyable tiles; charged shot and power-ups; game
over and final scores; difficulty, starting level and boss chosen in the waiting
room; sound effects and music; lobby, rooms and a waiting room; administration
console with bans and a white list; key remapping and auto-fire; a main menu
with settings, accessibility options, how to play and credits; a graphical
launcher; a Windows build in the CI.

## 10. What we would do differently

- **Snapshots**: start with delta compression in mind, as the 5 kB/s test shows the
  limit of full snapshots.
- **Handshake**: add the challenge token from the start. It is cheap to design and
  closes the main known weakness of the protocol.
- **Content**: levels, weapons and enemies are data files, but a new sprite or a
  new behavior still needs C++. Scripting would be the next step.
- **Sanitizers in the CI**: AddressSanitizer on the tests costs one CI job and would
  back up the claims of [section 6](#6-security).
